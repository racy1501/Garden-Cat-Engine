# 🌸 花园与猫咪 v5.2.0

一座 AI 与人类共享的治愈系花园：一起种花、经营，等猫咪来访、收养并照顾它。
AI 与人类共用同一座花园与便签，AI 还能用真实收获的鲜花制作花束、附上小卡片送给你，花束与卡片会被长期收藏。

## v5.2.0 发布介绍

- 17 种花与 12 款正式花束：种花、收获、发现配方，制作花束后选择赠礼或上架经营花店。
- 花店支持营业时间、货架扩容和保鲜设备；保鲜设备延后折价，不延长上架后 24 小时的报废期限。
- 花园 / 花店 / 小屋三地点共用同一存档。花店内分为「花束 / 赠礼」，花束内分为「货架 / 制作」。
- 共同小屋 v1-B 与家具商店：9 件金币购买家具、4 件花卉奖励装饰，逐步点亮小屋，不提供属性或经营加成。
- 猫咪从来访、决定留下等待取名，到免费正式收养；通过补充粮水、摸猫、零食、玩具和设施照料它，收养后还会外出归来。
- 16 种猫咪藏品、12 封顺序来信，以及花园压花和事件纪念；新发现有提示，便签、赠礼花束与卡片可以随时回看。

## 共享便签如何识别双方

花园服务不额外建立第二套绑定系统。

集合 MCP 完成「人类账号 ↔ AI 账号」绑定后，应让双方访问同一个花园 `session_id`：

- AI/MCP 从 `/api/...` 入口访问，服务端自动记为 `ai`
- 人类网页从 `/web/...` 入口访问，服务端自动记为 `human`
- 客户端不提交 `sender`，不能自行伪装身份

便签按 `session_id` 汇入同一条时间线。两端的冷却按发送方分别计算。

## 两种入口

### 人类玩家

直接打开网站根地址：

```text
https://你的域名/
```

首次进入时创建花园。服务器会生成：

- `session_id`：花园编号
- `garden_token`：这座花园的人类网页钥匙

两者默认保存在浏览器 `localStorage`。请使用页面中的「花园存档码」另行备份。

### AI / MCP

完整说明：

```http
GET /api/info
```

由人类先在网页创建花园，再把有效的 `session_id` 提供给 AI。AI/API 端不能注册或创建新存档。
AI 使用 `X-API-Key` 和该 `session_id` 调用正式 API。

查询正式商品 / 物品 ID：

```http
GET /api/catalog
X-API-Key: <全局密钥>
```

购买时使用目录中 `flowers` / `items` 对象的 key 作为商品 ID，不使用中文商品名。

执行普通游戏命令：

```http
POST /api/cmd
X-API-Key: <全局密钥>
Content-Type: application/json

{"session_id": "sess_xxxxxxxxxxxx", "command": "status"}
```

### AI 便签命令

```text
notes       查看第 1 页
notes 2     查看第 2 页
note 今天的薄荷开花了
```

也可直接调用：

```http
GET /api/notes?session_id=你的ID&page=1
X-API-Key: <全局密钥>
```

```http
POST /api/notes
X-API-Key: <全局密钥>
Content-Type: application/json

{"session_id": "你的ID", "content": "今天的薄荷开花了"}
```

## AI 花束规则

配方涉及的花种都至少收获过一次后，才会发现该花束；制作时还需有足量鲜花。
使用 `craft_bouquet` 制作后，花束进入花束库存（bouquet inventory），可选择赠送或在花店营业时上架：

```text
craft_bouquet bouquet_id=first_meeting
gift_bouquet instance_id=<花束实例ID> message=给你的春天
list_bouquet instance_id=<花束实例ID>
```

赠送和上架二选一。也可使用现有的 `make_bouquet` 查看已发现配方及材料情况，或直接制作并送给人类：

```text
make_bouquet
make_bouquet bouquet_id=first_meeting
make_bouquet bouquet_id=first_meeting message=给你的春天
```

- 制作消耗真实鲜花库存，每束共 3 朵；只有材料与解锁条件满足时才会扣除并记录。
- 赠礼不产生金币、不提供属性奖励，花束与卡片永久收藏。
- 花店上架花束可成交获得金币，会随新鲜度折价；从上架起经过 24 小时仍未售出的花束报废，闭店不暂停老化。
- 正式 12 款花束：初见、晨光、晴野、心笺、晚风、柔云、蓝信、樱枝、春宴、春山、月下书、彼岸诗。
- 暖阳、紫雾、小花园只作为旧存档历史赠礼兼容展示，不进入正式制作目录。
- 每次赠送保存一条永久记录，包含花束 ID、实际花材快照、送出时间和可选卡片留言。
- 同款花束可以重复赠送并累计数量；花束收藏的点亮状态和数量都从赠送历史派生，不另存图鉴进度。
- 卡片留言完全可选，也可以只送花束。
- 花店的「赠礼」内可回看赠礼花束与卡片；统一图鉴包含花卉与花束。
- AI 新赠送花束后，页面显示轻量“新”提醒；人类查看赠礼后消除提醒。升级前已有的花束历史默认已读。
- 首次查看新赠礼时，对应花束与新卡片会显示轻量“新”标记；查看后再次进入时标记消失。
- AI 成功赠送花束时，会在花园手记留下对应的重要事件记录。
- 新花束赠礼属于花园的重要互动事件，可在现有提醒与花园手记中呈现。
- 单束花束详情会展示该花束最近一次附带的卡片；若最新赠送没有卡片，则显示该花束历史中最近一张有内容的卡片。

## 便签规则

- 内容长度：1～20 个 Unicode 字符
- 冷却：AI 2 小时、人类 2 小时，各自计时
- 排序：最新到最旧
- 分页：每页 10 条
- 保存：独立 `garden_notes` 表，不塞进主存档 JSON
- 修改：不支持
- 单条删除：不支持
- 重开花园：便签保留
- 开启全新花园：便签保留，花园进度按新花园规则重置
- 带猫搬家：保留猫咪名字和已收养状态，其余花园进度重新开始
- 本地移除保存记录：只会清除当前浏览器里的本地凭据，不宣传物理删除整座花园

## 环境变量

正式部署需要：

- `GARDEN_API_KEY`：AI API 使用的全局密钥
- `DATABASE_URL`：PostgreSQL 连接地址；不配置时使用项目内本地 SQLite
- `PORT`：服务监听端口，默认 8080

人类网页不会读取或展示 `GARDEN_API_KEY`。

## 部署说明

本仓库（GitHub）是项目的正式源码与交付源；除本地运行外，项目也支持任何人自行部署，部署平台不限。

基础安装与启动：

```text
pip install -r requirements.txt
gunicorn game_api:app
```

- 数据库通过 `DATABASE_URL` 配置 PostgreSQL 连接即可，不绑定任何特定数据库服务。
- 程序启动时会自动创建新的 `garden_notes` 表；数据库数据独立于代码更新，普通代码更新不会清空已有花园存档。
- 部署完成后，直接打开部署地址（如 `https://你的域名/`）即可游玩。

## 关键时间规则

- 摸猫冷却：现实 10 分钟
- 心情单次离线结算：最多前 2 个现实小时
- 便签冷却：AI 与人类各自现实 2 小时
- AI 写入新便签后，人类网页的「便签」入口显示轻量「新」角标；人类打开便签查看后消除提醒。
- 未读判断使用后端持久化的人类最后查看游标，刷新网页不会丢失或凭空恢复；旧存档首次建立游标时已有便签默认视为已读。
- 花瓶保鲜：现实约 12 小时
- 虫害在种植时确定，达到触发点后暂停生长，治疗后从原进度继续。
